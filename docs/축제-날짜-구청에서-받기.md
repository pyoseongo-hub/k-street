**2026-09-12 사장님 지시:** "관광공사 말고 해당구청봐"

---

## 왜 관광공사로는 안 되나 — 쟀다

우리는 2026-09-01부터 매일 한국관광공사(`searchFestival2`)를 부르고 있었다.
그런데 2026-09-11에 확인해 보니 —

```
✅ 심각한 문제 없음 (startDate · location 다 갖췄거나, 행사로 내지 않았다)
   ⏳ 아직 0곳이다 — 관광공사에 올해 회차가 안 올라왔다는 뜻이고, 정상이다.
```

**올해 확정 날짜가 올라온 우리 축제가 0곳이었다.**
관광공사 축제 창구는 행사가 정리된 뒤에 채워지는 자리라,
손님이 정작 알고 싶은 **「이번 주에 열리나」**를 못 알려 준다.

사장님 말이 정확했다 — 축제를 **주최하는 쪽**이 가장 먼저 안다.

## 25개 구청을 따로 긁지 않는다 — 한 자리에 모여 있다

구청 홈페이지는 도메인도 생김새도 제각각이다:

| 구 | 문화관광 주소 |
|---|---|
| 성동구 | `www.sd.go.kr/tour/` |
| 중구 | `www.junggu.seoul.kr/tour/` |

25개를 따로 긁으면 **25개가 따로 망가진다.** 한 곳이 개편할 때마다 우리가 고쳐야 한다.
사장님이 쓸 수 있는 시간을 생각하면 이 길은 처음부터 안 된다.

**그럴 필요가 없다.** 서울시 문화포털(`culture.seoul.go.kr`)이
**구청과 구 문화재단이 직접 등록하는 자리**이고,
그게 서울 열린데이터광장 `culturalEventInfo` 로 그대로 나온다.

2026-09-12에 실제로 불러서 확인한 것:

```
list_total_count            19,525   (문화행사 전체)
CODENAME 이 「축제…」인 것    1,492
```

| 축제 | 올린 곳(ORG_NAME) | 등록일 | 행사일 |
|---|---|---|---|
| 2026 동작 빵도동 축제 | **동작문화재단** | 8/31 | 10/31 |
| 2026 서울 바비큐 페스티벌 | 서울시청 | 9/8 | 10/24~25 |
| 2026 윤동주문학제 | **종로구청** | 8/18 | 10/17~18 |
| 2026 생활예술축제 춤추는광진 | **광진문화재단** | 8/18 | 10/17 |

📌 **등록일과 행사일의 간격을 보라.** 2~6주다.
사장님이 말한 *"고지가 몇일전에 올라오거나 하니"* 가 숫자로 그대로 보인다.
그래서 **매일 본다.** 어제 없던 날짜가 오늘 생긴다.

## 두 창구를 다 쓴다 — 관광공사를 끄지 않았다

| | 관광공사 | 서울시 문화포털(구청) |
|---|---|---|
| 누가 올리나 | 관광공사가 정리 | **구청·구 문화재단이 직접** |
| 언제 올라오나 | 늦다 | **확정되는 대로** |
| 담는 범위 | 전국 대표 축제 | 서울 25구, 작은 동네 행사까지 |
| 우리 축제 확정 날짜 | **0곳** | 받는 중 |

**담는 축제가 서로 다르다.** 그래서 둘을 같이 둔다.
겹치면 **구청 쪽이 이긴다** — 주최자가 직접 올린 것이 더 앞선 사실이다.

## 🚨 이름으로 이을 수밖에 없다 — 그래서 더 깐깐하게

관광공사 쪽은 `contentId`로 이었다. 여기는 **공통 번호가 없다.**
이 저장소가 이름 대조로 여러 번 데인 자리라(NFC 분해형·띄어쓰기·옛 이름),
네 겹으로 막았다:

1. **정확히 맞은 것만 저장한다.** 비슷한 것은 저장하지 않고 「사람이 볼 후보」로만 낸다
2. **구(GUNAME)까지 같아야 한다** — 이름이 겹치는 행사가 다른 구에 있다
3. **NFC 정규화를 맨 앞에** — 자모 분해형이 섞이면 한 건도 안 맞는다
4. **지난 날짜는 아예 안 받는다** — 작년 회차를 올해처럼 보여 주면 헛걸음이다

대조하기 전에 이름을 다듬는다. 문화포털 제목은 이렇게 온다:

```
[성동문화재단] 2025 서울숲 재즈 페스티벌
 └ 기관 ┘  └연도┘ └───── 우리가 아는 이름 ─────┘
```

그래서 `[기관]` · `(부가)` · 연도 · `제N회` · 띄어쓰기를 걷어내고 비교한다.

## 🔑 열쇠가 있어야 돈다 (공짜)

`SEOUL_OPEN_API_KEY`. https://data.seoul.go.kr → **인증키 신청** (즉시 발급).

🛑 **시험용 `sample` 열쇠로는 안 된다.** 되는 줄 알고 그 길을 만들어 뒀는데,
2026-09-12에 80곳을 돌렸더니 전부 이랬다:

```
INFO-100  인증키가 유효하지 않습니다.
```

한두 번은 봐 주지만 그 뒤로는 막는다. 손으로 한 번 눌러
「어떻게 생긴 자료인가」를 보는 데까지다.

넣는 자리: 저장소 → **Settings → Secrets and variables → Actions**
→ New repository secret → 이름 `SEOUL_OPEN_API_KEY`

넣고 나면 **매일 06:00(한국 시각)**에 저절로 돈다.
열쇠가 없는 동안은 워크플로가 **조용히 지나간다** — 매일 빨간 X 가 뜨면
메일이 쌓이고, 그러면 진짜 실패도 안 읽게 되기 때문이다.
